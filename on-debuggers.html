On debuggers

They are my absolute favourite tool for understanding any codebase. You can simply run the code in the debugger and it can immediately transport you to the most interesting part of the code.

For example, you will learn about bwa and other alignment tools in block 2; I frequently use a debugger to jump to the core algorithms in the source code to understand them. You might (or might not) be surprised to find out that most source code is not interesting. It's usually code to read and write files, parse options, catch bad input, report errors, print extra stuff if something goes wrong, etc. etc.... The actual important algorithms are often only a small fraction of a production codebase.

gdb and lldb

When you look up debugging tools, many people will be talking about "gdb" or "lldb". These are general purpose debuggers that can debug Python, C, Rust - pretty much any programming language. However, they are somewhat complicated to use for anything except C or C++. Many core bioinformatics tools (aligners like bwa, minimap, utilities like samtools, and so on) are written in C, so if you are interested in how they work, you may want to check out these debuggers at some point.

Python

For python, you have many choices of great debugging tools. You can use the built in debugger in VS Code (most other fully featured code editors have something similar if you don't use VS Code) but I find it unintuitive. Python comes packaged with "pdb" (python debugger), but you may prefer "pdbp" (python debugger plus) which shows you which line of code you are on, colours the syntax, and various other nice features.

To install it:

pip install pdbp

To use it, let's say you have some script confusing_script.py, you can start debugging like this:

python3 -m pdbp confusing_script.py

If the script has arguments, you can just use these as normal:

python3 -m pdbp confusing_script.py -k6 -o out.csv

Commands

Once in the debugger, the most frequent commands I use are:

next (shortcut: n)
Evaluates the current line, jumps program pointer to next line.
step (shortcut: s)
Steps into the function on the current line. E.g., if the current line is: 
output = some_function(x, y)
The "next" command will evaluate the function and go to the next line, while the "step" command will jump into the function and you can investigate how it works.

Beware! If you are importing functions from a package, e.g. numpy, many of them will be very complex. Some will mix python with other code (e.g., C++). If you try to "step" into these you might not find anything useful...

break <break_position> (shortcut: b)
Automatically stops the program as soon as it reaches break_position. You can use it to break on a function e.g. break some_function or you can use it to break on a line e.g. break 112 will stop the program on line 112.

You can also add a condition, so the program only stops when the condition is true. E.g. break some_function, x == 5 will only stop in some_function when x is 5, and break 112, i > 1000 will only stop on line 112 once i is above 1000. This is very useful inside loops, where you don't want to stop on every iteration.

continue (shortcut: c)
The program will run as normal until it hits a breakpoint, or until the end of the program.
clear
Clears all the breakpoints you have set.
p <expression> (short for print)
Prints the value of expression, e.g. p output. Usually you can just type the expression on its own, and pdbp will print it. The catch is when a variable has the same name as a debugger command (e.g. n, s, c, b): if the variable exists, typing c prints it, but if it doesn't exist (yet), typing c runs the continue command and the program runs off! p c is always safe: it prints the variable, or tells you it isn't defined.

You can also evaluate regular python code, e.g.:

output[10]

to print the 11th value of whatever is inside "output".

For more, the pdbp README shows what pdbp looks like and its extra features, and the official pdb documentation has the full list of commands (they all work in pdbp too). If you prefer a tutorial, Real Python's Python Debugging With Pdb is a good walkthrough.

Debugging exercises

These exercises use a simple O(n2) string matching algorithm implemented in Python (z.py).

(optional) If you want a bit of background, you can read the first chapter of Dan Gusfield's textbook "Algorithms on Strings, Trees and Sequences"

This is a git repository. If you have changed the code and want to reset everything, just run:

git restore .

2. Conditional breakpoints

Run the same command as in exercise 1. The program finds a match at index 6.

Stepping into z_naive for every i would take forever. Instead, set a breakpoint with a condition:

break z_naive, i == 11

continue, and step through the loop. Why is it that i == 11 gives a match at index 6 of the search string?

3. What is the $ for?

Change this line:

concat_string = query + '$' + search

to:

concat_string = query + search

Run with ACTG TTGATCACTGCCGAT again. The match should be at index 6. What index do you get?

Use the debugger to print concat_string and z_array and explain what went wrong.

Now run with ACTG TTACTGTT. There is clearly a match at index 2, but why is the match missed?

4. Debugging a crash

In z_naive, change < to <=:

while i + k <= len(seq) and seq[i + k] == seq[k]:

Try running it with AC GAC (or any other input you like). The program crashes if you run it on the command line, but try running it in the debugger - it will stop at the crash and let you inspect what happened! (very very useful)

Now put the < back, but swap the order of the two conditions:

while seq[i + k] == seq[k] and i + k < len(seq):

Run it again. Does the order matter?
